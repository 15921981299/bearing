## 1. 工程师身份（你已确认有具名工程师）

### 需要提供

| 字段 | 说明 | 注意 |
|---|---|---|
| `name` | 真实姓名 | 与本人确认用中文名拼音还是英文名 |
| `role` | 真实职务 | **不要拔高**。写「应用工程师」就别写「首席工程师」 |
| `credentials` | 3–5 条可核验履历，每条一句 | 只写能对证的：年数、服务过的行业/设备类型、在公司负责什么 |
| `bio` | 2–3 句，写他具体做什么决策 | 例：审图、确认检验范围、签发生产放行 |
| `yearsExperience` / `joinedYear` | 从业年数 / 入司年份 | 可只填其一 |
| `photo` | 本人照片，方形 ≥ 640×640 | 你或工厂自己拍，**不要用图库人像** |
| `sameAs` | **LinkedIn 等外部可核验档案** | ⭐ 最高价值的一项 |
| `knowsAbout` | 3–6 个技术领域 | 例：combined roller bearings、mast guide selection |
| `consentOnFile` | 本人是否同意公开署名与照片 | **必须为 true 才渲染** |
| `reviewAuthor` | 是否作为全站署名的技术审核人 | 通常设 1 人 |

### 为什么 `sameAs` 最关键

具名但无处可查的作者，Google 判为「不可核验」，E-E-A-T 收益基本归零。
一条能打开的 LinkedIn / 专利 / 期刊 / 会议讲师页，胜过十条加粗的资历描述。
如果工程师没有 LinkedIn，下面任选其一也能成立：

- 行业协会会员页
- 期刊/会议署名
- 专利公开页（中国专利公布网站）
- 工厂官网上他署名的技术页

### 需要我做什么

把上表信息发我，我直接填进 `team.ts` 并跑一次构建验证。或你自己照 `team.ts` 顶部的注释模板填。

⚠️ 提醒：人离职后要把它 `consentOnFile` 改回 `false`，否则会留下一个「已离职的现任工程师」——比没有更糟。

## 2. 工厂检验照片

现在的 4 张里，2 张是车间、2 张只是量具外观。**不足以证明"在检验"**。要拍的是**过程**，不是设备照片。

### 拍摄清单（建议 6–10 张）

| # | 画面 | 必须同时入镜 | 为什么 |
|---|---|---|---|
| 1 | 检验台全景，人在操作量具测某型号 | 型号标识 / 工单 | 证明是"人在检"，不是空台 |
| 2 | 量具读数的特写 | **读数清晰可读** + 被测件 | 这是最有说服力的一张 |
| 3 | 同批次零件整齐摆放待检 / 已检 | 批号标签 | 证明批量而非单件摆拍 |
| 4 | 三坐标或光学仪器的测量界面 | 屏幕上的实测数值 | 仪器级证据 |
| 5 | 硬度计 / 金相试样（如有） | 试样与读数 | 材料证据 |
| 6 | 内/外径、游隙检测 | 塞规/百分表 + 件 | 常规尺寸证据 |
| 7 | 包装前贴标与装箱 | 标签上的型号/批号 | 衔接发货 |
| 8 | 检验记录单填写 | 报告号（可模糊） | 文书证据 |

### 硬要求

1. **必须是你或工厂自己拍的**。网上找的图 = 和编造姓名同性质的造假。
2. **不要 P 掉关键信息**：读数、型号、批号要能看清。模糊背景可以，模糊证据不行。
3. **不要消除水印**后当自有素材用 —— 现有 2 张车间图已注明"legacy watermark removed"，这一步以后不要再做。
4. 每张配上 `capturedOn`（拍摄日期）与 `batch`（画面里的批号），**照片就从装饰变成证据**。

### 交付格式

WebP 或 JPG，长边 ≤ 1600px（站点会自动压缩），放到 `public/images/factory-facility/`，然后告诉我文件名与上面三项信息。

## 3. 可公开检验报告（你已确认走「脱敏真实样本」）

### 选哪两份

建议覆盖两类，最能呼应采购方的问题：

1. **一份尺寸检验报告** —— 选一个搜索量大的型号（如 4.063 / 4.054 / PR4.056 这一类）
2. **一份材料/热处理类报告**（如有）—— 证明不只是测尺寸

### 必须保留（这是价值所在，一个都不能删）

报告编号 · 出具机构 · 受检型号 · 批次 · 检验日期 · 检验依据（图纸版本/标准号）· 使用仪器 · 实测数值 · 判定结论 · 审批签字

### 必须脱敏

客户名称 · 单价 · 数量 · 订单号 · 任何第三方标识

脱敏后用 PDF 存放：`public/downloads/inspection-reports/<文件名>.pdf`

### 需要告诉我的

报告编号、出具机构、型号、批次、日期、依据、仪器、实测值（几行即可）、审批人（写职务即可）、**你遮蔽了哪些字段**（会明示在页面上："Redacted before publication: …"）。

### 绝对不能做

- ❌ 拿别的厂 / 别的型号的报告顶替
- ❌ 把规格值抄成"实测值"
- ❌ 发一份没签字的报告（无签字不构成报告）
- ❌ 发工厂从未实测过的型号

## 4. 客户应用案例

**你这次没勾选这一项**，所以现在的 5 篇仍然是「品类应用参考」——它们刻意不写客户、数量、时间、结果，是**诚实但不具备案例说服力**的写法。

要升级成真正的客户案例，需要三样之一：

| 你有 | 可以写成 | 需要客户同意吗 |
|---|---|---|
| 客户书面同意具名 | 「XX 公司 桅杆轴承替换项目」+ 行业+工况+结果 | 需要（建议留书面记录） |
| 只有成交记录，不便具名 | 「某欧洲叉车维修商：4.054 系列年用量替换项目」+ 工况+结果 | **不需要**，但要确保记录真实 |
| 只有询盘，未成交 | 保持现在的「应用参考」写法 | 不需要 |

### 一个案例页需要包含

- 应用场景（设备类型 + 部位，如"三级门架侧向导向"）
- 问题（原厂件交期长 / 尺寸不符 / 磨损异常）
- 我们做了什么（型号替代、图纸复核、检验范围）
- 结果（可量化优先：交期天数、装配合格率、复购批次）
- **脱敏口径声明**（和报告一样，明示你遮蔽了什么）

### 底线

不写"为某某知名公司供货"除非真的供货且书面同意。这类不实陈述对方可追责，且属于我们自己在竞品报告里批过的"为密度而编造"。

# 6. 草稿已生成 —— 你只需要替换 `[REPLACE: …]`

四类信号的**草稿记录**已经写进数据文件，页面、结构化数据、导航、sitemap 全部接好。
草稿不会进部署产物，具体机制见下。

## 6.1 两条硬规则

| 规则 | 实现 | 效果 |
|---|---|---|
| 标了 `draft: true` 的记录**不进任何部署构建** | `src/data/publish-mode.ts` → `draftPreviewEnabled` | Cloudflare 的构建命令不带环境变量，所以草稿到不了线上 |
| 已发布记录里**不许残留 `[REPLACE: …]`** | `assertNoPendingFields()` 在数据层抛错 | 构建直接失败，而不是把编造内容发出去 |

第二条刻意写在**数据层**而不是构建脚本里：只要页面 import 了这个数据文件就会触发，所以即使有人直接跑 `astro build`、绕过 npm 生命周期脚本，也一样被拦住（已实测：两种路径都会中止构建）。

另外还有一条针对署名作者的闸门：**作为全站审核人的作者必须有 `sameAs`**（LinkedIn／专利／期刊／会议页任一）。具名但查不到的人，E-E-A-T 收益基本归零，所以构建拒绝发布。

## 6.2 怎么看草稿长什么样

```bash
npm run build:draft-preview    # 草稿可见，页面顶部有 DRAFT 标记条
npm run audit:publish          # 只读审计：已发布/草稿数量、缺什么、还差几张照片
npm run build                  # 正式构建：草稿被排除，占位符被检查
```

预览构建里，每条草稿记录旁边会直接列出**它还差什么**（黄框提示），等于把待办清单挂在页面上。

## 6.4 报告样本的两个细节

1. **`pdf` 现在是可选项**。没填 PDF 路径时不渲染下载链接（避免死链）。脱敏稿放到 `public/downloads/inspection-reports/` 后再把路径填进 `pdf`。
2. **`redacted`（脱敏字段清单）我故意留成占位符**。页面上会原样打印「Redacted before publication: …」，如果清单和实际遮蔽的不一致，那就是一句不实陈述——所以这一项必须你自己核对后写。
